# 01. Предпосылки, доступы и решения “до старта”

Документ помогает подготовить всё необходимое **до настройки** Asana/Rocket.Chat/n8n, чтобы внедрение не застопорилось на правах, токенах и несогласованных правилах.

---

## 1) Кому это нужно прочитать

- Инженер‑внедренец (вы) — основной исполнитель.
- PM(ы) команды — согласуют правила статусов, тексты уведомлений, пороги “красных” случаев.
- Администратор Asana — даёт права и помогает с AI Teammates/полями.
- Администратор Rocket.Chat — даёт права на webhooks и сервисного пользователя.
- (Опционально) IT/Sec — согласует размещение n8n и хранение токенов.

---

## 2) Минимальные требования и лицензии

### Asana
- Доступ к рабочему пространству/организации Asana с правами:
  - создавать проекты/секции
  - создавать кастомные поля
  - создавать/управлять задачами
- **Asana Intelligence / AI Teammates** должны быть доступны в вашей подписке/поставке.
  - Если Teammates недоступны, интеграцию (создание задач и уведомления) можно внедрить, но блок “AI‑подсказки” будет ограничен.

### Rocket.Chat
- Доступ администратора или права на:
  - создание/настройку интеграций (Outgoing Webhook)
  - создание сервисного пользователя/бота
  - выдачу токена (Personal Access Token или эквивалент, зависит от версии/настроек)

### n8n (технический слой, без пользовательского UI)
- Доступ к среде размещения (self‑hosted или managed).
- Возможность хранить секреты (токены) безопасно.
- Доступ к интернету/сетям так, чтобы:
  - Rocket.Chat мог отправлять HTTP POST на webhook n8n
  - n8n мог обращаться к Asana API и Rocket.Chat REST API

## 3) Что нужно решить заранее (чек‑лист решений)

### 3.1 Каналы и коммуникация (anti‑spam)
- [ ] Канал Rocket.Chat для входящих запросов (рекомендуемо: `#task-requests`)
- [ ] Канал/личка для срочных уведомлений PM (рекомендуемо: отдельный закрытый канал `#pm-alerts`)
- [ ] Правило: инициатор получает только статусы **создано / нужны уточнения / отклонено / завершено** (и опционально “критично изменён срок”)
- [ ] Правило: “красные” уведомления в Rocket.Chat — **только PM**, без широких упоминаний команды

### 3.2 Asana: структура и стандарт задачи
- [ ] Имя входного проекта: **“Inbox from Rocket.Chat”**
- [ ] Секции: `New` → `Triaged` → `In Progress` → `Done`
- [ ] Минимальный стандарт описания задачи (Definition of Ready/Done):
  - [ ] краткое резюме
  - [ ] критерии готовности / чек‑лист (DoD)
  - [ ] срок (или явная отметка “нужны уточнения”)
  - [ ] ответственный (или “не назначен” до решения PM)

### 3.3 Пороги “красных” случаев (конфиг мониторинга)
Выберите значения на старте (потом их легко менять):

- [ ] \(X\) = “скоро дедлайн”, дней до due date (рекомендуемо: 2)
- [ ] \(Y\) = “нет прогресса”, дней без обновлений (рекомендуемо: 2)
- [ ] Кулдаун для однотипного алерта по одной задаче (рекомендуемо: 24 часа)
- [ ] Расписание cron‑проверки (рекомендуемо: каждые 4 часа в рабочее время или 2–4 часа круглосуточно)

### 3.4 Как фиксируем “Blocked”
Выберите **один** простой, проверяемый механизм:

- Вариант A (рекомендуемо): кастомное поле `Blocked` (Yes/No)
- Вариант B: ключевое слово в комментарии (`blocked`, `блокер`, `blocked:`)
- Вариант C: отдельный статус/секция (не рекомендуется на старте, усложняет процесс)

## 4) Модель данных: что и куда пишем

### 4.1 Что приходит из Rocket.Chat
Из входящего сообщения (и контекста треда при необходимости):

- текст сообщения
- автор
- время
- `message_id`
- `thread_id` (или id треда/корневого сообщения, зависит от Rocket.Chat)
- ссылка на тред/сообщение (если возможна генерация)

### 4.2 Что создаём/храним в Asana
В задаче Asana сохраняем:

- `name`: черновое название (из первой строки или “Запрос из Rocket.Chat”)
- `notes/description`: полный текст + метаданные (автор/дата) + ссылка на Rocket.Chat тред
- кастомные поля:
  - `Source = Rocket.Chat`
  - `Rocket.Chat Link = <url>`
  - (опц.) `Priority`, `Type`, `Blocked`
- служебная связка для идемпотентности (см. следующий раздел)

---

## 5) Идемпотентность (как избегаем дублей)

Ключевое правило: **одно сообщение/тред = одна Asana‑задача**.

Рекомендуемый ключ дедупликации:

- `dedup_key = message_id + ":" + thread_id`

Где хранить ключ:

- В n8n Data Store (или эквиваленте), чтобы при повторном webhook не создавать новую задачу.
- Дополнительно можно сохранять `message_id`/`thread_id` в описание задачи или в кастомные поля (если есть подходящее поле).

---

## 6) Доступы и секреты (минимальные требования)

### 6.1 Asana токен
- Создайте отдельный технический токен/интеграцию.
- Права: минимально необходимые (создание задач, чтение/поиск задач, чтение полей).

### 6.2 Rocket.Chat токен
- Отдельный сервисный пользователь (бот).
- Права:
  - писать сообщения в нужные каналы
  - писать ответы в треды
  - (опц.) упоминать PM (если политика команды разрешает)

### 6.3 Хранение токенов
- Токены храним **только** в секретах/credential‑хранилище n8n (не в текстах workflow, не в чатах).
- Доступ к n8n ограничиваем администраторам интеграции.

---

## 7) Минимальный “Definition of Done” для внедрения (перед пилотом)

- [ ] Канал/процесс согласован с PM (anti‑spam правила утверждены)
- [ ] Asana проект Inbox создан и доступен нужным людям
- [ ] Rocket.Chat outgoing webhook отправляет события в n8n
- [ ] Workflow A создаёт задачу и отвечает ссылкой в тред
- [ ] Workflow B шлёт “красные” алерты PM с кулдауном (без дублей)
- [ ] Есть тестовый чек‑лист кейсов (см. `07_operations_testing_rollout.md`)
