# 04. Настройка n8n (размещение, безопасность, креды, Data Store)

n8n — это “тонкий мост” без пользовательского UI. Пользователи по‑прежнему работают **только** в Rocket.Chat и Asana.

В этом документе — **практические шаги**, чтобы n8n был:

- доступен для webhooks из Rocket.Chat/Asana
- безопасен (секреты, доступы)
- наблюдаем (чтобы быстро чинить сбои)

---

## 1) Выберите способ размещения

Варианты:

- **Managed n8n** (проще, быстрее запуск)
- **Self-hosted** (больше контроля, часто выбирают для enterprise)

Для задания/пилота обычно достаточно managed, но если политика компании требует self-hosted — выбирайте его.

---

## 2) Требования к доступности и сети

Должно быть возможно:

- Rocket.Chat → HTTP POST на webhook URL n8n (workflow A)
- Asana → HTTP POST на webhook URL n8n (workflow C, если используете Asana webhooks)
- n8n → HTTPS запросы к:
  - Asana API
  - Rocket.Chat REST API

Если Rocket.Chat/Asana находятся за VPN/внутренней сети — заранее согласуйте маршрутизацию.

---

## 3) Базовая безопасность (обязательно)

### 3.1 Доступ к UI n8n
- Включите вход по логину/паролю (или SSO, если доступно).
- Дайте доступ только администраторам интеграции.

### 3.2 HTTPS
- Webhook URL должен быть по HTTPS.

### 3.3 Секреты
- Токены Asana и Rocket.Chat храните только в credential‑хранилище n8n.
- Не вставляйте токены в “текстовые поля” workflow.

### 3.4 Ограничение источников (по возможности)
- Ограничьте, кто может дергать webhook URL (IP allowlist / firewall / reverse proxy rules).
- Добавьте проверку “секретного токена” для Rocket.Chat webhook (см. `03_rocketchat_setup.md`).

---

## 4) Подготовьте credentials (подключения) в n8n

Создайте 2 набора credentials:

### 4.1 Asana API
- Тип: HTTP Header Auth / Bearer Token (как поддерживает ваша версия n8n)
- Значение: Asana Personal Access Token (или токен интеграции)
- Права токена: минимум — создание задач, поиск/чтение задач, чтение кастомных полей

### 4.2 Rocket.Chat REST API
- Тип: HTTP Header Auth
- Заголовки зависят от вашей версии Rocket.Chat:
  - либо `Authorization: Bearer <token>`
  - либо `X-Auth-Token` + `X-User-Id`
- Проверьте на тестовом запросе (см. `05_workflow_A_intake.md`, шаг “Ответ в тред”).

---

## 5) Включите Data Store (для дедупа и кулдаунов)

В решении Data Store нужен для:

- дедупликации событий intake (не создавать дубль задачи)
- кулдауна “не чаще 1 раза в 24 часа” для алертов
- записи “мы уже отправляли уведомление о завершении”

### Какой формат данных хранить (рекомендуемо)
Сделайте 3–4 “таблицы”/коллекции (или key‑space):

1) `rc_dedup`
   - key: `dedup_key = message_id + ":" + thread_id`
   - value: `{ asana_task_gid, created_at, rc_room_id, rc_thread_id }`

2) `asana_to_rc` (обратный индекс для уведомлений из Asana)
   - key: `asana_task_gid`
   - value: `{ rc_room_id, rc_thread_id, dedup_key }`

3) `alert_cooldowns`
   - key: `asana_task_gid + ":" + alert_type`
   - value: `{ last_sent_at }`

4) `completion_notified` (если используете workflow C)
   - key: `asana_task_gid`
   - value: `{ notified_at, rc_room_id, rc_thread_id }`

Если ваша версия n8n не поддерживает “Data Store” как встроенный модуль — используйте встроенное хранилище/kv или минимальную внешнюю БД (но это уже усложнение; сначала проверьте наличие Data Store).

---

## 6) Наблюдаемость и аварийные уведомления

### 6.1 Execution history
- Включите сохранение истории исполнений (минимум на пилот).
- Настройте retention (например, хранить 7–14 дней, чтобы не раздувать хранилище).

### 6.2 Error workflow / уведомления об ошибках
Сделайте правило:

- если workflow падает (ошибка API/таймаут), n8n уведомляет PM/админа в `#pm-alerts` **одним сообщением** с:
  - названием workflow
  - временем
  - краткой причиной
  - ссылкой на execution (если доступно)

---

## 7) Итоговый чек‑лист готовности n8n

- [ ] n8n доступен по HTTPS
- [ ] UI защищён (логин/пароль/SSO), доступ ограничен
- [ ] Созданы credentials: Asana API, Rocket.Chat API
- [ ] Есть Data Store (или эквивалент) для дедупа/кулдаунов
- [ ] Включена история исполнений, настроены уведомления об ошибках в `#pm-alerts`
