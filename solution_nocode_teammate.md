# Решение (Asana‑native): Rocket.Chat ↔ Asana с Asana Intelligence/Teammates как “мозгом”

(Пользовательские интерфейсы остаются **только Rocket.Chat и Asana**. Роли **Инициатор / PM / Исполнитель** сохраняются. AI предлагает и анализирует, решения принимает человек.)

## 1. Контекст и ограничения (что важно по заданию)

**Сохраняем:**
- Инструменты для пользователей: **только Rocket.Chat + Asana**
- Роли: **Инициатор, PM, Исполнитель** (ответственности не меняем)
- Общая логика: **запрос → создание задачи → контроль → завершение**
- Формат: структурированный текст без кода

**Ключевое допущение (для упрощения и “Asana‑native”):**
- В Asana доступны **Asana Intelligence / Teammates** (в т.ч. агент для координации задач и анализа рисков) и они могут работать с контекстом Work Graph (проект, статусы, сроки, комментарии, зависимости, история изменений).

### 1.1 Какие AI‑возможности Asana используются “из коробки” (для информативности)

Ниже — те возможности **Asana Intelligence / AI Teammates**, на которые опирается это решение (без разработки собственных моделей/LLM):

- **Контекст и рассуждение в рамках Asana (Work Graph)**: Teammate использует контекст задач/проектов/статусов/истории изменений, чтобы давать релевантные рекомендации.
- **Рекомендации и координация работы**: Teammate выступает как “координатор” — подсказывает, что уточнить, как структурировать задачу и какие действия PM предпринять при рисках.
- **Прозрачность и контроль**: AI работает внутри Asana и подчиняется правилам доступа; решения по критическим полям остаются за PM (human‑in‑the‑loop).

Полезные официальные материалы Asana (обзорные, “что это и как работает”):
- Asana: [Introducing Asana AI Teammates](https://asana.com/ru/inside-asana/introducing-asana-ai-teammates)
- Asana resources: [AI Teammates overview](https://asana.com/resources/ai-teammates-overview)

## 2. Обзор решения (в одном абзаце)

Инициатор пишет запрос в Rocket.Chat.
Интеграционный слой реализуется **в n8n** (под капотом, без пользовательского UI): он принимает событие из Rocket.Chat, создаёт задачу в Asana и связывает её с тредом Rocket.Chat.
Дальше **Asana Teammate** помогает PM быстрее привести задачу к стандарту (резюме, чек‑лист, вопросы, риски) и подготовить решения по критическим полям (назначение/срок/приоритет), но **утверждает их PM**.
Для контроля выполнения AI используется как “анализатор” внутри Asana (объяснения рисков и рекомендуемые действия), а Rocket.Chat используется как канал прозрачных статусов и точечных уведомлений без шума.

## 3. Архитектура (минимальная, Asana‑native)

### 3.1 Компоненты

- **Rocket.Chat (UI для людей)**
  - Канал для запросов (например, `#task-requests`)
  - Треды по запросам
  - Интеграция Rocket.Chat типа **Outgoing Webhook** для отправки событий о новых сообщениях в n8n
  - Сервисный пользователь/токен для отправки сообщений обратно в Rocket.Chat через REST API (публикация ответа в тред)

- **Asana (UI для людей)**
  - Проект(ы) для задач
  - Кастомные поля (минимум): `Source=Rocket.Chat`, `Rocket.Chat Link`, `Priority`, `Type` (опционально `Risk`)
  - **Asana Intelligence/Teammates**:
    - Teammate “Task Coordinator” (триаж, качество описания, мониторинг прогресса/рисков, рекомендации PM)

- **Интеграционный слой (без UI, “тонкий мост”)**
  - Принимает событие о новом сообщении из Rocket.Chat и создаёт задачу в Asana
  - Публикует ответы/уведомления из Asana обратно в Rocket.Chat (в тред или в канал PM)
  - Реализуется “под капотом” как **n8n‑workflows**:
    - **Webhook Trigger** (вход от Rocket.Chat Outgoing Webhook)
    - **HTTP Request** к Asana API (создание/поиск задач)
    - **HTTP Request** к Rocket.Chat REST API (ответы в тред, уведомления PM)
    - **Cron Trigger** (периодическая проверка “красных” событий)
    - **Data Store** (дедуп + кулдауны + журнал отправок)
  - Никакого нового пользовательского UI не появляется; пользователи по‑прежнему работают только в Rocket.Chat и Asana

### 3.2 Asana‑native упрощение структуры проектов

Чтобы убрать сложную маршрутизацию на старте, вводим один “входной” проект:
- **Asana проект: “Inbox from Rocket.Chat”**
  - Секции: `New` → `Triaged` → `In Progress` → `Done`
  - Teammate/правила Asana помогают PM делать триаж и (при необходимости) перемещать задачи в целевые проекты

Это резко снижает сложность интеграции: интеграционному слою не нужно знать все проекты/секции.

## 4. Процесс после автоматизации (пошагово)

### Этап 1: Приём запроса (Rocket.Chat)

1) **Инициатор** пишет сообщение в `#task-requests` (желательно с коротким контекстом: “что нужно / зачем / срок / кому”).

2) Rocket.Chat отправляет событие о новом сообщении в n8n через **Outgoing Webhook** (HTTP POST на n8n Webhook URL). n8n проверяет:
- сообщение из нужного канала
- не бот/не служебное
- идемпотентность: `message_id + thread_id`

3) n8n создаёт задачу в Asana (в “Inbox from Rocket.Chat”) и заполняет минимум:
- `name`: черновое название (из первой строки или краткое “Запрос из Rocket.Chat”)
- `description`: полный текст сообщения + метаданные (автор/дата) + ссылка на тред
- поля: `Source=Rocket.Chat`, `Rocket.Chat Link`, служебные идентификаторы (`message_id`, `thread_id`)

4) В Rocket.Chat (в тред) бот пишет: “Черновик задачи создан в Asana: <ссылка>”.

### Этап 2: Авто‑улучшение задачи (Asana Teammate)

Teammate внутри Asana предлагает “приведение к стандарту” (как черновик/подсказки для PM):
- **короткое резюме** (1–3 абзаца)
- **критерии готовности** / чек‑лист
- предложения по `Type`, `Priority`, `due date`, исполнителю/команде
- 1–3 **вопроса для уточнения**, если данных не хватает

Важно: это **предложения**. Критические поля (срок/исполнитель/приоритет) считаются подтверждёнными только после явного решения PM.

**AI‑возможности Asana “из коробки”, используемые на этапе:**
- **Контекст и рассуждение (Work Graph)**: Teammate видит поля/комментарии/историю изменений задачи в Asana и на их основе формирует предложения.
- **Рекомендации и координация**: Teammate предлагает структуру, вопросы и варианты заполнения полей; финальное решение остаётся за PM.

### Этап 3: Решение PM (human‑in‑the‑loop)

PM получает минимальный “action list” (в Asana и/или в Rocket.Chat, по выбору канала коммуникации):
- **Approve**: “ОК, создаём/фиксируем как предложено”
- **Edit**: поправить срок/исполнителя/приоритет/формулировки
- **Ask**: задать уточняющий вопрос инициатору (через тред Rocket.Chat)
- **Reject**: отклонить запрос с причиной

Рекомендованный минимализм:
- подтверждение PM происходит в Asana (родной UI)
- интеграционный слой публикует итог решения в Rocket.Chat (в тред), чтобы инициатор видел статус

**AI‑возможности Asana “из коробки”, используемые на этапе:**
- **Прозрачность и контроль**: AI‑подсказки видны в Asana, но решение по критическим полям принимает PM.

### Этап 4: Работа и обновления (Исполнитель в Asana)

Исполнитель ведёт задачу в Asana (статус, комментарии, чек‑лист). Это остаётся как в текущем процессе компании.

### Этап 5: Системный контроль выполнения (Teammate → Rocket.Chat)

Контроль построен так, чтобы PM тратил минимум времени на “разбор”, а Rocket.Chat не превращался в поток уведомлений:

**A) Ежедневный обзор для PM (в Asana)**
- PM открывает проект “Inbox from Rocket.Chat” (или список задач `Source=Rocket.Chat`)
- Teammate помогает быстро получить сводку: что “горит”, почему и что делать дальше (как рекомендации внутри Asana)

**AI‑возможности Asana “из коробки”, используемые на этапе:**
- **Контекст и рассуждение (Work Graph)**: Teammate использует историю задач/комментарии/статусы для объяснения “почему горит”.
- **Рекомендации и координация**: Teammate предлагает действия PM (что уточнить/кого пинговать/какой следующий шаг).

**B) Точечные уведомления в Rocket.Chat (только “красные” случаи)**
- n8n отправляет PM сообщение в Rocket.Chat только по сильным событиям:
  - просрочка (due date < сегодня и задача не `Done`)
  - близкий дедлайн без прогресса (до due date ≤ X дней и `modified_at` старше Y дней)
  - явный блокер (кастомное поле/маркер `Blocked=true` или ключевые слова в последнем комментарии)
- сообщение всегда содержит ссылку на задачу в Asana и короткий контекст; детали/рекомендации PM смотрит в Asana (Teammate)

**Как бот детектит “красные события” (прозрачно и проверяемо)**
- **Источник данных**: только Asana поля/метаданные задачи: `due_on`/`due_at`, `completed`, `modified_at`, `assignee`, (опционально) кастомное поле `Blocked`, последние комментарии (ограниченно).
- **Триггер в n8n**: **Cron Trigger** (например, каждые 2–4 часа).
- **Как выбираются задачи**: n8n запрашивает из Asana все незавершённые задачи с `Source=Rocket.Chat` (или из проекта “Inbox from Rocket.Chat”) и для каждой применяет правила “красного” события.
- **Почему нужен cron‑чек**: правило “modified_at старше Y дней” — временное условие; его надёжно выявляет только периодическая проверка.
- **Пороговые значения (конфиг)**:
  - \(X\) — “скоро дедлайн” (например, 2 дня)
  - \(Y\) — “нет прогресса” (например, 2 дня)
  - при желании можно сделать \(X/Y\) зависимыми от `Priority`, но базовая версия держит одно значение для минимализма.

### Этап 6: Завершение

При переводе задачи в `Done`:
- инициатор получает уведомление в тред Rocket.Chat (“готово” + ссылка)
- задача исключается из мониторинга, напоминания прекращаются

## 5. Как AI работает с данными (и что считается корректным)

### 5.1 Какие данные используются

**Из Rocket.Chat** (через интеграцию):
- текст запроса + (при необходимости) контекст треда
- автор, канал/комната, время
- `message_id`, `thread_id` для трассируемости

**Из Asana** (внутри Work Graph):
- статус/секция, сроки, исполнитель, история изменений
- комментарии/активность, чек‑листы, зависимости (если есть)
- контекст проекта/правил команды

### 5.2 Корректный результат

**Для одного запроса:**
- В Rocket.Chat видна цепочка статусов: “принято → создан черновик в Asana → подтверждено/уточнение/отклонено”
- В Asana существует **ровно одна** задача, связанная с тредом Rocket.Chat (link + ids)
- Критические параметры (срок/исполнитель/приоритет) подтверждены PM либо явно помечены как “требует уточнения”

**Для контроля:**
- PM получает **один** ежедневный обзор (в Asana) и только “красные” уведомления в Rocket.Chat
- Срочные сообщения — только “красные”
- Дубликатов уведомлений нет (кулдауны/дедуп)

## 6. Логика контроля выполнения (Asana‑native)

### 6.1 Оценка риска и выявление проблем (без неподтверждённой “магии”)

Проблемы выявляются по **простым проверяемым сигналам** в Asana (статусы/сроки/активность), а Teammate используется для объяснения и рекомендаций внутри Asana:
- просрочка / близкий дедлайн
- отсутствие активности/изменений
- явные признаки блокера (поле/маркер/текст в комментариях)
- зависимости (ждём другие задачи)
- конфликт ответственности (нет assignee / владелец не определён)

Teammate помогает PM быстро получить:
- “что не так” (2–3 причины)
- “что сделать” (1–2 действия)

### 6.2 Действия при рисках (строго human‑in‑the‑loop)

Teammate **не меняет критические поля сам**. Он:
- формулирует рекомендации
- предлагает готовые сообщения/вопросы
- PM подтверждает действие (например: “напомнить исполнителю”, “перенести срок”, “переназначить”, “эскалировать”)

Коммуникация с людьми идёт через Rocket.Chat: PM отправляет сообщение сам или через бота/сервис (если команда разрешает такой режим).

## 7. Исключение лишнего шума (anti‑spam)

**Правила коммуникации:**
- Инициатор: только события “создано / нужны уточнения / завершено / изменён срок (если критично)”
- Исполнитель: напоминания только по решению PM или при “красном” риске (по политике команды)
- PM: ежедневный обзор в Asana + срочные “красные” в Rocket.Chat

**Технический механизм:**
- дедуп по `message_id + thread_id`
- кулдауны: не чаще 1 раза в 24 часа для однотипных алертов по одной задаче
- журнал отправок (служебный, без UI): хранится в n8n (Data Store или эквивалент)

## 8. Где процесс может сломаться (и что делаем)

1) **Неструктурированный запрос**
- Teammate не может предложить срок/исполнителя/критерии готовности
- Действие: Teammate предлагает 1–3 вопроса; PM отправляет их в тред Rocket.Chat → статус “нужны уточнения”

2) **Дубли событий/повторные запросы**
- Обнаружение: запись уже существует по `message_id + thread_id`
- Действие: вернуть ссылку на существующую задачу, не создавать новую

3) **Права/ошибка интеграции**
- Обнаружение: ошибка создания/публикации сообщения
- Действие: ретраи с backoff; после порога — уведомление PM в Rocket.Chat + ручной режим

4) **Ошибки/неточности AI**
- Обнаружение: предложения Teammate противоречат входным данным/политикам
- Действие: PM всегда подтверждает критические поля; при спорном — запрос уточнений

## 9. Практическая польза и измеримость

**Экономия времени PM:**
- Создание задачи: вместо 5–8 минут → 30–90 секунд (проверить предложение Teammate и подтвердить)
- Контроль: вместо нерегулярных 15–30 минут/день → 5–10 минут/день на дайджест + точечные “красные”

**Метрики:**
- среднее время “сообщение в Rocket.Chat → задача в Asana”
- доля задач, где Teammate предложил корректного исполнителя/срок (и доля правок PM)
- количество уведомлений PM/день (контроль шума)
- доля просрочек по задачам `Source=Rocket.Chat` (до/после)

## 10. Пошаговое внедрение (минимально)

### Шаг 0: Стандарты (30–60 минут)
- выбрать канал `#task-requests` и канал/личку для дайджестов PM
- определить минимальный стандарт описания задачи (что должно быть в результате: резюме/DoD/чек‑лист)

### Шаг 1: Asana (1–2 часа)
- создать проект “Inbox from Rocket.Chat” + секции
- добавить кастомные поля: `Source`, `Rocket.Chat Link`, `Priority`, `Type` (опционально `Risk`)
- включить/настроить Teammate “Task Coordinator” (политика: что он предлагает, а что требует подтверждения PM)

### Шаг 2: Rocket.Chat (30–90 минут)
- создать бота/сервисного пользователя
- настроить события о новых сообщениях (Integrations/Outgoing Webhooks)
- дать боту права писать в треды/каналы, упоминать пользователей

### Шаг 3: n8n (2–6 часов)
- развернуть n8n (self‑hosted или managed) и создать подключения к Rocket.Chat и Asana (через API токены)
- **Workflow A (Intake)**: Rocket.Chat webhook → дедуп (`message_id+thread_id`) → Asana “Create task” → Rocket.Chat “reply in thread” со ссылкой
- **Workflow B (Red alerts)**: Cron (каждые 2–4 часа) → Asana “List/search tasks” (`Source=Rocket.Chat`, не Done) → правила “красных” событий → кулдауны/журнал → Rocket.Chat уведомление PM

## 11. Почему это реалистично и минималистично

- Пользователи работают **только** в Rocket.Chat и Asana.
- Интеграция делает минимум (создать/связать/доставить уведомления).
- “Интеллект” и мониторинг сосредоточены в Asana (Teammate + Work Graph), что снижает количество внешней логики и уменьшает риск “расхождения истины”.
- Human‑in‑the‑loop сохранён: критические поля и эскалации подтверждает PM.
