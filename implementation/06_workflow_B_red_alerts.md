# 06. n8n Workflow B — Red alerts (Cron → Asana → Rocket.Chat)

Цель workflow B: системно отслеживать риски по задачам из Rocket.Chat и присылать PM **только “красные”** уведомления без шума.

“Красные” случаи из решения:

- **Просрочка**: due date < сегодня и задача не `Done`
- **Скоро дедлайн и нет прогресса**: до due date ≤ \(X\) дней и `modified_at` старше \(Y\) дней
- **Явный блокер**: `Blocked=true` (или ключевые слова в комментарии — опционально)

---

## 1) Подготовка

Должно быть готово:

- workflow A работает и заполняет `Source=Rocket.Chat` (или эквивалент)
- `#pm-alerts` существует и бот может туда писать
- В `04_n8n_setup.md` настроен Data Store `alert_cooldowns`
- Вы согласовали \(X\), \(Y\), cooldown (см. `01_prerequisites_and_decisions.md`)

## 2) Создайте workflow

Название: **Workflow B — Red alerts**

## 3) Узлы и логика — пошагово

### Узел 1: Cron Trigger
Рекомендуемая частота:

- каждые 4 часа (или 2–4 часа)  
- при желании — только в рабочее время

### Узел 2: Asana → Search/List tasks (получить активные задачи)
Нужно получить список задач, которые:

- находятся в проекте “Inbox from Rocket.Chat” (или помечены `Source=Rocket.Chat`)
- не завершены

Что важно выбрать в “fields” (чтобы не делать много дополнительных запросов):

- `gid`
- `name`
- `assignee` (имя/ид)
- `due_on` и/или `due_at`
- `completed`
- `modified_at`
- `permalink_url` (если доступно)
- `custom_fields` (чтобы прочитать `Blocked`, `Priority`, `Source`)

### Узел 3: Split in Batches / Iterate
Пройдитесь по задачам по одной (или батчами), чтобы:

- оценить риск
- проверить кулдаун
- при необходимости отправить уведомление

---

## 4) Правила “красных” событий (как считать)

### 4.1 Нормализация дат
Определите:

- “сегодня” (локаль/таймзона компании)
- due date задачи:
  - если есть `due_at` — используйте его
  - иначе `due_on` (считайте как конец дня в таймзоне компании)

### 4.2 Просрочка (alert_type = `overdue`)
Условие:

- due date < сейчас
- задача не завершена

### 4.3 Скоро дедлайн + нет прогресса (alert_type = `near_deadline_no_progress`)
Условие:

- due date − сейчас ≤ \(X\) дней
- `modified_at` старше \(Y\) дней

Примечание: `modified_at` — грубый, но проверяемый сигнал. Он подходит для минималистичной версии.

### 4.4 Blocked (alert_type = `blocked`)
Рекомендуемый вариант (без “магии”):

- кастомное поле `Blocked = true`

Опционально (если очень нужно):

- подтягивать последние комментарии (stories) и искать ключевые слова  
  Минус: больше API‑вызовов, выше риск шума и нагрузки.

---

## 5) Кулдауны (anti‑spam)

Для каждого alert_type по каждой задаче:

- key в Data Store: `asana_task_gid + ":" + alert_type`
- если `last_sent_at` < 24 часа назад → **не отправлять**
- иначе отправить и обновить `last_sent_at`

Рекомендуемая политика при нескольких проблемах одновременно:

- отправлять **один** алерт на задачу за запуск workflow, с приоритетом:
  1) `overdue`
  2) `blocked`
  3) `near_deadline_no_progress`

---

## 6) Отправка сообщения в Rocket.Chat (в `#pm-alerts`)

Минимальный формат сообщения:

- заголовок: “🔴 Риск по задаче”
- причина (1 строка): “Просрочка / Blocked / Скоро дедлайн без прогресса”
- кто владелец: assignee (или “не назначен”)
- срок: due date
- ссылка: Asana permalink

Шаблоны текста — в `09_message_templates.md`.

---

## 7) Ошибки и аварийные случаи

Если Asana API временно недоступен:

- workflow должен завершаться ошибкой
- n8n отправляет **одно** сообщение в `#pm-alerts` (см. `04_n8n_setup.md`)

---

## 8) Тест‑чек‑лист workflow B

1) Создайте тестовую задачу из Rocket.Chat (через workflow A).
2) Поставьте due date “вчера” → дождитесь cron‑запуска → должен прийти `overdue`.
3) Поставьте due date “завтра”, не трогайте задачу \(Y\) дней (или имитируйте, временно изменив пороги) → должен прийти `near_deadline_no_progress`.
4) Поставьте `Blocked=true` → должен прийти `blocked`.
5) Убедитесь, что повторный запуск в течение 24 часов **не** шлёт дубль.
