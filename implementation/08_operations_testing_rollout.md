# 08. Тестирование, пилот, запуск и эксплуатация (runbook)

Цель документа: чтобы внедрение прошло контролируемо, а поддержка не превратилась в “ручной огонь”.

---

## 1) Среды: пилот и прод

Рекомендуемо:

- **Пилот**: отдельный канал Rocket.Chat (`#task-requests-pilot`) и отдельный Asana проект (“Inbox from Rocket.Chat (Pilot)”).
- **Прод**: основные канал/проект.

Так вы проверите дедуп, форматы сообщений и пороги \(X/Y\) без влияния на рабочие задачи.

---

## 2) Тест‑план (чек‑лист)

### 2.1 Intake (workflow A)
- [ ] Новое сообщение → создаётся 1 задача в Asana → бот отвечает ссылкой в тред
- [ ] Повторный event (дубли) → новая задача не создаётся → бот пишет “уже создано”
- [ ] Сообщение от бота/служебного пользователя игнорируется (если включали фильтр)
- [ ] Ошибка Asana API → в `#pm-alerts` приходит аварийное сообщение

### 2.2 Red alerts (workflow B)
- [ ] Просрочка → 1 алерт PM
- [ ] Скоро дедлайн + нет прогресса → 1 алерт PM
- [ ] Blocked=true → 1 алерт PM
- [ ] Кулдаун 24 часа работает (повтора нет)

### 2.3 Status + completion (workflow C)
- [ ] `PM Decision=Need info` + комментарий “Вопрос инициатору:” → сообщение в тред
- [ ] `PM Decision=Rejected` + “Причина отказа:” → сообщение в тред
- [ ] `PM Decision=Approved` → (если включили) сообщение в тред
- [ ] `Done` → “Готово” в тред (один раз)

---

## 3) Пилот: как запускать безопасно

1) Выберите 1–2 PM и небольшой круг инициаторов.
2) Объявите простой регламент:
   - пишем запросы только в `#task-requests-pilot`
   - обсуждение — в треде
   - статусы/решения — в Asana
3) Включите workflow A (intake).
4) Через 1–2 дня включите workflow B (red alerts) с консервативными порогами (например, \(X=1\), \(Y=2\)).
5) После стабилизации включите workflow C (status + completion).

---

## 4) Go-live (переход в прод)

1) Зафиксируйте настройки:
   - канал `#task-requests`
   - проект Inbox
   - \(X/Y\), расписание cron, cooldown
2) Перенастройте Outgoing Webhook Rocket.Chat на прод‑URL workflow A.
3) Проверьте тестом 1 сообщение end‑to‑end.
4) Включите workflow B и C.

---

## 5) Наблюдаемость (что смотреть каждый день первую неделю)

- количество созданных задач/день
- доля дублей (дедуп сработал) — если много, ищем причину (Rocket.Chat шлёт повторные события?)
- количество “красных” алертов/день
- число ошибок workflow в n8n (execution failures)

---

## 6) Типовые проблемы и быстрые проверки

### “Сообщение в Rocket.Chat есть, задача в Asana не создалась”
- Проверить в n8n историю исполнения workflow A:
  - дошёл ли webhook?
  - упал ли запрос к Asana? (401/403/429/5xx)
- Проверить токен Asana (не истёк ли, есть ли доступ к проекту)

### “Создаются дубли задач”
- Проверить:
  - правильно ли извлекаются `message_id` и `thread_id`
  - совпадают ли значения при повторном событии
  - работает ли запись/чтение `rc_dedup` (Data Store)

### “Не приходит ответ в тред Rocket.Chat”
- Проверить права бота (писать в канал/тред)
- Проверить, что вы используете правильные поля для thread reply (в зависимости от версии Rocket.Chat)

### “Слишком много алертов PM”
- Увеличить cooldown (например, до 48 часов для некоторых типов)
- Ужесточить правила: требовать `Blocked=true` вместо анализа текста
- Поднять пороги \(X/Y\)

---

## 7) Rollback (если что-то пошло не так)

Быстрый откат без потерь:

1) Выключить workflow A (intake) в n8n.
2) Отключить Outgoing Webhook в Rocket.Chat.
3) PM возвращается к ручному созданию задач (как в текущем процессе).
4) Уже созданные задачи в Asana остаются, ничего не ломается.

---

## 8) Минимальные правила эксплуатации (ownership)

Назначьте ответственных:

- владелец интеграции (1 человек): токены, доступы, n8n
- бизнес‑владелец процесса (PM‑лид): правила уведомлений, пороги, формат запросов

Рекомендация: раз в месяц коротко пересматривать:

- \(X/Y\) и cooldown
- шаблоны сообщений
- долю просрочек и пользу для PM
